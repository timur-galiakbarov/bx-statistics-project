# Деплой

Каждый пуш в `master` сразу выкатывается на прод (socstat-lab.ru). Отдельного шага релиза нет: что попало в `master`, через несколько минут работает у пользователей. Деплой можно запустить и вручную — `workflow_dispatch` в GitHub Actions.

## Как проходит

Workflow `.github/workflows/deploy.yml`, окружение `production`:

1. По SSH заливает репозиторий на сервер в `DEPLOY_PATH` (по умолчанию `/opt/socstat`) через `rsync --delete`. Не копируются `.git`, `.github`, `node_modules`, сборки `dist` и `api/.env` — секреты живут только на сервере.
2. Если на сервере нет `api/.env`, создаёт его из `deploy/api.env.production.example` и падает: секреты нужно заполнить и перезапустить workflow.
3. `docker compose -f docker-compose.prod.yml up -d --build --remove-orphans` пересобирает и перезапускает контейнеры.
4. До минуты ждёт `GET /api/health` на `127.0.0.1:4000`. Не дождался — выводит состояние и последние 200 строк логов `api`, `mongo`, `redis` и помечает деплой упавшим.

Новый пуш, пока предыдущий деплой идёт, отменяет его (`concurrency: socstat-production`) — выкатывается последний коммит.

## Что работает на сервере

`docker-compose.prod.yml`: `frontend` (nginx со сборкой фронта, порт 8080), `api` (порт 4000), `mongo` 7 и `redis` 7 с данными в томах `mongo-data` и `redis-data`. Порты открыты только на `127.0.0.1`, снаружи запросы принимает nginx сервера (пример конфига — `deploy/nginx/socstat.conf.example`). Миграции данных выполняются при старте API (`api/src/db/migrations.ts`).

Сейчас проект лежит в `/home/socstat.ru` (`DEPLOY_PATH`), контейнеры называются `socstatru-*`.

Напрямую Telegram с сервера недоступен, поэтому API ходит в него через SOCKS5 (`TELEGRAM_PROXY_HOST`/`TELEGRAM_PROXY_PORT` в `api/.env`). Это касается и MTProto, и Bot API контент-плана. Это не контейнер, а systemd-сервис `socstat-socks.service` на хосте: SSH-туннель `ssh -N -D 172.18.0.1:1080` до внешнего сервера. При его перезапуске открытые соединения gramjs умирают молча, от зависания очереди защищает таймаут задач — см. [snapshots.md](snapshots.md#зависшие-запросы).

## Кэш сборок и место на диске

Каждый деплой пересобирает образы прямо на сервере, и BuildKit складывает слои сборки в свой кэш (`/var/lib/docker/buildkit`, `/var/lib/containerd`). Сам он не чистится: за сентябрь–ноябрь 2026 кэш вырос до 12,9 ГБ (0,3–1 ГБ на пуш, в день трёх пушей — 3 ГБ), и свободное место на 40-гигабайтном диске упало с 15 до 11 ГБ, хотя образы весят всего 2 ГБ.

Чтобы кэш не рос безгранично, на сервере включён встроенный garbage collector BuildKit — `/etc/docker/daemon.json`:

```json
{
  "builder": {
    "gc": {
      "enabled": true,
      "defaultKeepStorage": "5GB"
    }
  }
}
```

`dockerd` постоянно проверяет размер кэша и выкидывает самые давно использованные слои, как только тот превышает 5 ГБ. Свежие слои остаются, поэтому деплой по-прежнему собирается из кэша; образы, контейнеры и тома не затрагиваются — `docker system df` показывает их отдельными строками, а в строке Build Cache видно только кэш.

Настройка применяется только через `systemctl restart docker`: конфиг билдера не перечитывается на `reload`. Контейнеры с `restart: unless-stopped` поднимаются сами, сайт недоступен ~15 секунд.

Проверка и ручная чистка:

```bash
docker system df                  # строка Build Cache
docker buildx du --verbose        # записи кэша по датам создания
df -h /                           # свободное место
docker builder prune -af          # разово удалить весь кэш
docker builder prune -f --filter until=168h   # только старше недели
```

## Настройки

- Секреты репозитория: `DEPLOY_HOST`, `DEPLOY_PORT` (по умолчанию 22), `DEPLOY_USER`, `DEPLOY_SSH_KEY`; переменная `DEPLOY_PATH`.
- Переменные API на сервере — `api/.env`, шаблон в `deploy/api.env.production.example`.
- Лимит кэша сборок — `/etc/docker/daemon.json` на сервере (см. [Кэш сборок и место на диске](#кэш-сборок-и-место-на-диске)); в репозитории этого файла нет, он настраивается один раз при подготовке сервера.

## Заставка при недоступности

Если frontend временно недоступен, серверный nginx показывает автономную страницу `deploy/nginx/maintenance.html` с сообщением «Socstat.ru эволюционирует». Страница раз в пять секунд проверяет `/api/health` и обновляется, когда API снова отвечает успешно. Файл и его оформление не зависят от контейнеров и внешних ресурсов. Ответ сохраняет исходный статус ошибки и не кешируется. API и старые контроллеры продолжают отдавать обычные ошибки; уже открытая страница приложения автоматически заставку не покажет.

Для включения на сервере нужно перенести настройки из `deploy/nginx/socstat.conf.example` в действующий конфиг nginx, указать в `alias` реальный путь к файлу (сейчас `/home/socstat.ru/deploy/nginx/maintenance.html`), проверить `nginx -t` и перезагрузить конфигурацию. Пример использует `/opt/socstat`; сам деплой конфигурацию nginx не устанавливает. Если nginx или сам сервер недоступен, заставка не появится.

## Ограничения

- Отката нет: вернуть прошлую версию — это revert и новый пуш в `master`.
- Перед пушем в `master` изменение должно быть готово к проду; проверить, что деплой прошёл, можно во вкладке Actions на GitHub или по `https://socstat-lab.ru/api/health`.
