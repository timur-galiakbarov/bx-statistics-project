# «Сравнение»: UX-аудит и план перестройки

Дата: 30 сентября 2026. Статус: предложение для реализации, код приложения не изменён.

## Основание и границы

Изучены `src/pages/ComparePage.tsx`, `src/components/CompareChart.tsx`, `src/styles.css`, типы и сервисы аналитики VK / YouTube, маршрут сравнения, соседняя страница публикаций и `docs/ux-redesign.md`. Это экспертная оценка сценариев по реализации, не пользовательское исследование. Браузер в сессии недоступен: отображение, реальные задержки и поведение на устройствах не проверены. Конкурентные паттерны проверены по официальным публичным материалам; платные кабинеты не тестировались.

## Продуктовая цель

За минуту после загрузки SMM-специалист должен понять своё положение среди выбранных конкурентов, найти публикации для изучения и получить материал для отчёта клиенту.

Основные сценарии:

1. Еженедельная проверка: «Как мы выглядим на фоне тех же конкурентов?»
2. Подготовка контент-плана: «Какие публикации и форматы стоит изучить?»
3. Отчёт клиенту: «Как объяснить результат и подкрепить его примерами?»
4. Разовый аудит: «Сравнить несколько аккаунтов, пока не выбирая свой бренд».

Главный маршрут: положение бренда → наблюдение в данных → конкретные публикации → гипотеза для контент-плана или отчёт. Метрики не доказывают, что именно вызвало успех поста.

## Что уже полезно

- Поиск VK и YouTube, сравнение до десяти аккаунтов.
- Несколько периодов, сортировка, горизонтальная диаграмма.
- Частичный успех API: ошибка одного аккаунта не должна отменять остальные.
- Указание ограничений YouTube и недоступности отдельных показателей.
- API уже содержит публикации, дневные ряды и предыдущий период.

## Проблемы текущей реализации

| Приоритет | Наблюдение | Последствие для SMM | Изменение |
|---|---|---|---|
| P0 | Период переключается без обновления или пометки старого результата | Пользователь может принять старые цифры за новый период | Разделить черновик фильтров и применённый запрос; показывать даты результата и состояние обновления |
| P0 | `averageViewsPerPost` подписан «Средний охват» | В отчёт может попасть неверное утверждение про уникальную аудиторию | Назвать «Просмотры / пост»; охват показывать только при наличии соответствующих данных |
| P0 | `wall.isComplete` не используется страницей; доступность метрик учтена лишь частично | Неполная выборка и пропуски могут выглядеть как полноценные результаты | Единые правила пригодности метрик для таблиц, графика, рангов и выводов |
| P1 | Поиск и список занимают два верхних блока и остаются над результатами | Настройка мешает регулярной работе с анализом | После первого запуска сворачивать выбор в компактную панель |

| P1 | По умолчанию сортировка и график показывают сумму реакций | Большой аккаунт или частый постинг выглядит безусловно эффективнее | Стартовать с ER на пост, рядом показывать размер аккаунта и число публикаций; давать переключение на другие метрики |
| P1 | График всегда про реакции, даже при сортировке по ER или просмотрам | Таблица и график не образуют единое сравнение | Один выбор активной метрики для ранжирования и диаграммы |
| P1 | Три последовательные таблицы повторяют названия аккаунтов и дают 17 полей | Нужно удерживать строки в памяти и много прокручивать | Одна основная таблица; дополнительные показатели — в раскрытии |
| P1 | Только локальный `useState`, нет сохранения состава и периода | После ухода со страницы приходится собирать сравнение заново | Состояние в URL и последнее сравнение локально; затем наборы в аккаунте |
| P1 | Нет перехода из результата к публикациям с тем же контекстом | Вопрос «что у них сработало» требует нового ручного поиска | Топ публикаций прямо в сравнении и переход в «Публикации» с фильтрами |
| P1 | Есть только неделя, две недели, 30 дней | Неудобно готовить месячные отчёты | Текущий месяц, прошлый месяц, произвольные даты |
| P2 | `Warnings` показывает количество, а ошибки — ID и сообщение | Непонятно, чему можно доверять и как исправить проблему | «Качество данных», расшифровка по аккаунту и повторная загрузка |
| P2 | Одиннадцатый аккаунт молча отсекается через `slice(0, 10)` | Добавление выглядит сломанным | Явный лимит и отключённое добавление с объяснением |
| P2 | Пустая поисковая выдача не объясняется; добавленное не отмечено | Пользователь повторяет действия без обратной связи | «Ничего не найдено», «Добавлено», понятные подсказки |
| P2 | В мобильных стилях строки трёх таблиц превращаются в длинные карточки | Сопоставление одинаковой метрики между аккаунтами требует прокрутки | Мобильный рейтинг по одной метрике и раскрытие деталей |

Дополнительно: удаление аккаунта и смена платформы обнуляют результат; кнопка запуска доступна даже с нулём аккаунтов; у кнопок удаления отдельных аккаунтов нет доступного имени. При переключении платформы или редактировании состава во время запроса возможен показ ответа для уже неактуального выбора. Это нужно учесть в контракте состояния, а не исправлять отдельными подписями.

| 2 | Аккаунты | Компактные аватары и названия, метка «Мой бренд», добавление, счётчик лимита |
| 3 | Короткая сводка | ER на пост, просмотры на пост, публикации за период. Для каждой метрики — свой результат и медиана конкурентов; место — только по явно названной метрике |
| 4 | Наблюдения | Не более трёх коротких проверяемых фактов; каждый ведёт к подтверждающей таблице или публикациям |

### Первый визит и настройка

Вместо двух пустых панелей — понятный старт: «Сравните свой бренд с конкурентами». Предложить аккаунты, уже сохранённые пользователем, поиск по названию / ссылке и вставку нескольких ссылок. Опорный аккаунт необязателен: для разового исследования доступен режим «Все на равных».

На каждый выбранный аккаунт — аватар, платформа, название и отметка добавления. До двух аккаунтов кнопка запуска недоступна, рядом подсказка «Добавьте ещё один аккаунт». На лимите — «Выбрано 10 из 10 — удалите один, чтобы добавить другой».

После первого запуска настройка сворачивается. Состав редактируется в отдельной панели с «Применить» и «Отмена», чтобы выбор нескольких конкурентов не запускал серию дорогих запросов. Удаление и очистка допускают отмену. Для VK и YouTube сохраняются отдельные последние наборы.

### Обзор

Одна таблица: аккаунт, подписчики, публикации, ER на пост, просмотры / пост, взаимодействия / пост. Абсолютные суммы, лайки, комментарии и репосты доступны в деталях. «Фото» и «Видео» из отдельных медиаразделов не выдавать за долю форматов публикаций.

Свой бренд выделен меткой и мягким фоном, имеет постоянный цвет. Активная метрика управляет сортировкой и горизонтальной диаграммой; полное название аккаунта доступно без обрезания смысла. Диаграмма показывает медиану конкурентов. Таблица — точные значения. Не вводить непрозрачный общий «балл эффективности».

ER по подписчикам полезен для первого взгляда, но не делает аккаунты автоматически сопоставимыми: рядом должны оставаться объём аудитории и число постов. При недоступном ER предлагать просмотры или взаимодействия на пост и объяснять причину.

Для десяти аккаунтов диаграмма увеличивается по высоте; названия и числа читаемы. Таблица имеет закреплённую шапку и колонку аккаунта. На телефоне — та же выбранная метрика, ранжированные строки и раскрытие аккаунта, а не повторение всех таблиц карточками. Управление доступно с клавиатуры; смысл не кодируется только цветом.

### Наблюдения и контент

Пример текста на условных данных: «ER вашего бренда — 1,2%; медиана трёх конкурентов — 0,8%. Разница +0,4 п.п.». Кнопка: «Смотреть публикации». Наблюдение вычисляется по явному правилу, без необходимости подключать генеративную модель.

Вкладка «Контент» содержит лучшие публикации выбранных аккаунтов: превью, автор, дата, выбранная метрика, ссылка на оригинал. Фильтры: аккаунт, формат, маркированная реклама для VK, сортировка по ER / просмотрам / взаимодействиям. «Показать все» открывает раздел публикаций с сохранением состава и периода; потребуется поддержка параметров в этом разделе.

Для следующих этапов: сравнение результата поста с типичным результатом этого же аккаунта, сохранение идеи с заметкой, рубрики и темы. Такой режим помогает не заполнять ленту исключительно постами крупнейшего конкурента. Делать вывод о «лучшем формате» только вместе с количеством публикаций и достаточностью выборки; пороги проверить на данных и исследовании.

### Динамика

Один график, одна метрика. По умолчанию свой бренд и до двух выбранных конкурентов; остальные включаются явно. Не рисовать десять неразличимых линий.

Текущие дневные ряды публичных постов описывают метрики публикаций, сгруппированных по дате выхода. Это не прирост просмотров или реакций в конкретный день. Заголовок и подсказка должны отражать это различие. Истинная динамика накопления потребует исторических снимков.

### Отчёт

Первый этап: CSV таблицы и «Скопировать сводку» с датами, составом, определениями метрик и ограничениями. Затем компактный PDF: три главных наблюдения, сравнительная таблица и выбранные публикации. PDF требует отдельной реализации и проверки макета.

Именованные наборы вида «Клиент → конкуренты» сохраняют аккаунты, опорный бренд, платформу и настройки. URL хранит конфигурацию для восстановления; ссылка на конфигурацию сама по себе не является общедоступным снимком отчёта. Публикуемые отчёты с отдельным доступом — самостоятельная будущая задача.

## Правила доверия к данным

1. Всегда показывать точные даты результата. Черновик периода не меняет подпись уже загруженных данных.
2. Периоды «Предыдущий месяц» и «Этот месяц» доступны наряду с последними 7 / 30 днями. Произвольные даты должны проходить серверную валидацию; текущие сервисы ограничивают диапазон 93 днями.
3. Просмотры не равны уникальному охвату. Взаимодействия VK = лайки + комментарии + репосты; YouTube = лайки + комментарии. Формулы доступны из подписи метрики.
4. Текущий ER на пост рассчитывается относительно текущего числа подписчиков. Он не является историческим ER относительно размера аудитории на дату публикации.
5. Публичные показатели — накопленные на момент сбора значения у публикаций выбранного периода. Сравнение двух периодов описывает две группы публикаций разного возраста, а не чистый прирост взаимодействий за эти периоды. Дельты помечать соответствующим образом; не обещать исторические срезы.
6. `0`, «нет публикаций», «нет доступа», «частичная выборка» и «метрика не поддерживается» — разные состояния. Если постов нет, средний ER / просмотры на пост не равны доказанному нулю эффективности.
7. Учитывать `isComplete`, `previous.wall.available`, `availability` и `unavailableMetrics`. Непригодные значения исключать из рангов, медиан и выводов, а не подменять нулём. Для каждого ориентира указывать число пригодных конкурентов.
8. При неполных лайках или комментариях составной показатель взаимодействий и ER тоже требует статуса неполноты. Единый селектор должен определять пригодность метрики до её форматирования.
9. Медиана считается по выбранным сопоставимым конкурентам, исключая свой бренд. При одном конкуренте писать «сравнение с …», при отсутствии пригодных данных не показывать ориентир. Нельзя называть такую выборку отраслевым бенчмарком.
10. Разница ER по умолчанию — в процентных пунктах. Процентное изменение при нулевой базе не считать; показывать абсолютную разницу или «нет базы для сравнения».
11. Сравнивать аккаунты внутри платформы; не объединять VK и YouTube в единый рейтинг ER. Недоступные платформенные метрики скрывать, а не заполнять таблицу одинаковыми «Недоступно».
12. «Рекламные посты» означает наличие платформенной маркировки. Отсутствие маркировки не доказывает отсутствие продвижения.

## Состояния взаимодействия

- Нет результатов поиска: явное сообщение и пример допустимой ссылки.
- Загрузка: сохранение применённого контекста и предыдущего результата с пометкой обновления; на первом запуске — скелет структуры.
- Частичная ошибка: успешные аккаунты остаются, у проблемного — название, объяснение и «Повторить». Если успешный только один, явно сказать, что полноценное сравнение пока невозможно.
- Изменение фильтров: новый запрос связан с неизменяемым снимком параметров; ответ старого запроса игнорируется.
- Повторное посещение: восстановить набор и настройки, заново проверить актуальность данных. Не показывать сохранённые числа как свежие.
- Прогресс «3 из 5 загружено» показывать только при реальных событиях загрузки. Текущий API возвращает один общий ответ; для честного прогресса нужен другой контракт.

### Технические зависимости

- Для сводки, сравнительной таблицы, базовых наблюдений, дневных рядов и публикаций значительная часть данных уже есть в `CommunityAnalytics`.
- Произвольные даты: расширить `api/src/routes/compare.ts` и `compareService.ts`, передать `dateFrom` / `dateTo` в сервисы обеих платформ. Одного календаря на фронтенде недостаточно.
- Сохранённые аккаунты уже загружаются в `App`; использовать их в выборе вместо повторного поиска.
- Уточнить типы: YouTube фактически возвращает строковые ID публикаций и `null` для некоторых метрик, тогда как общие типы местами объявляют числа. Исправить контракт до универсальной сортировки и карточек.
- Время обновления сейчас не является явным полем результата сравнения: добавить метаданные получения / кэша, не выдумывать свежесть на клиенте.
- Backend обрабатывает аккаунты последовательно. После замера задержек рассмотреть кэш и ограниченный параллелизм с учётом лимитов платформ; не обещать ускорение до измерений.
- Исторический рост подписчиков у конкурентов, динамика накопления реакций и честное сравнение постов в одинаковом возрасте требуют дополнительных исторических данных.
- Не использовать отдельные счётчики загруженных фото и видео как готовую аналитику форматов постов. Форматы считать по публикациям и учитывать смешанные вложения.

## Как проверить, что стало лучше

Провести два коротких раунда с 5–7 SMM-специалистами, ведущими несколько аккаунтов: на текущем сценарии и на прототипе. Это качественная проверка, не статистическое доказательство. Задания:

1. Добавить свой бренд и трёх конкурентов, выбрать прошлый месяц.
2. Объяснить, у кого выше ER и насколько свой бренд отличается от конкурентов.
3. Найти два поста, которые хочется разобрать для контент-плана.
4. Подготовить краткую сводку для клиента.
5. Вернуться и повторить аудит того же состава за другой период.

Предлагаемые цели, подлежащие проверке: не менее 80% участников выполняют ключевые задачи без подсказок; первый осмысленный вывод — за минуту после загрузки; два релевантных примера постов — за три минуты; восстановление набора — без повторного поиска.

Измерять отдельно время настройки, серверное ожидание и время интерпретации. События: создание / восстановление набора, завершение загрузки, смена метрики, открытие подтверждающих постов, копирование / экспорт отчёта. Главный продуктовый сигнал — повторное использование сохранённого сравнения вместе с успешным выполнением задач, а не просто число кликов по диаграмме.

Перед выпуском проверить: 2 и 10 аккаунтов; длинные одинаковые названия; пустой период; скрытые метрики; нулевая база; неполная история; ошибка одного / всех аккаунтов; быстрая смена платформы и периода; перезагрузка страницы; клавиатура и мобильный экран.
